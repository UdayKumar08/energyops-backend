# Local API

The local API lets a screen, or curl, try the agents without any of the production machinery. It exists so that the agent playground page can be built against something real, and it is meant to run on a developer's own computer and nowhere else. There is no sign-in yet, so it protects itself in three ways. It refuses to be created unless the environment is `local`, `python -m energyops.api` listens on 127.0.0.1 only and has no option to change that, and it answers only requests whose Host header is `127.0.0.1` or `localhost`, which stops a web page on another site from reaching it through DNS rebinding. When real authentication arrives these guards stay, and a deployed API becomes a separate piece of work.

Start it with `uv run python -m energyops.api` (add `--port 8001` to change the port), then open http://127.0.0.1:8000/docs for the generated reference. It needs no database. It reads provider keys from your local `.env` each time they are needed, so adding a key does not require a restart.

The endpoints are small. `GET /health` reports the environment. `GET /providers` lists the model choices and whether each one has a key, without ever showing the key. `GET /agents` and `GET /agents/{id}` return the registry fields of an agent (name, domain, status, capabilities, model, prompt version) and, for one agent, its full spec, its prompt text with a fingerprint, and any guardrails the spec switches on that are not implemented. `POST /agents/{id}/runs` runs an agent once and returns the full run record with its trace. What a run needs depends on the agent's `input_kind`, which `GET /agents` reports: an agent with kind `question` takes a `question`, one with kind `audience` (the report writer) takes an `audience` of `manager` or `technical` and defaults to `manager`, and one with kind `anomaly` (the anomaly investigator) takes an `anomaly_id` such as `A1`. Sending the wrong kind, such as a question to the report writer, is a 422 and nothing runs. `GET /anomalies?site=demo-clinic` lists the events the detector finds for a site, so a screen can offer them to choose from. An event id that the site does not have is a normal failed run with the error kind `unknown_anomaly`, not an HTTP error. Every run also takes an optional site, a provider and an optional exact model name. A run also takes `data_access`, which is `mcp` by default, meaning the agent starts the read-only energy MCP server and calls its tools to get the fact sheet (see docs/mcp.md), or `direct`, which computes the same fact sheet in Python for comparison. The playground page has a Data access choice for it. `GET /runs` and `GET /runs/{id}` read finished runs back.

The provider defaults to `test`, the labelled test adapter. It makes no network call and returns a canned correct answer, and its runs are recorded with the provider `test-adapter`, so a screen can be built and tried for free and its output can never be mistaken for a real model's. Choosing `gemini` or `nebius` makes a real call and uses a little free quota. If the key is missing the API answers 503 and names the setting to add.

A run that fails its checks, for example because the model invented a figure or the provider was unavailable, is a normal result. The API answers 200 with a record whose status is `failed` and whose `error_kind` says why. HTTP errors are kept for problems with the request itself.

Run records are held in memory, the newest 200, and are lost when the server stops. Storing them in the database is part of the backend phase. The agent list comes from the registry in `energyops/agents/registry.py`, which holds the energy analyst, the report writer and the anomaly investigator today and never more than five.

## The playground page

Opening http://127.0.0.1:8000/ takes you to a plain page at `/playground` that uses these endpoints. An agent picker at the top of the page switches between the agents. It shows the agent's Basic, Configuration and Guardrails tabs and a Runs tab, and beside them a panel where you pick a model, then either type a question, choose an audience for a report, or choose one of the detected events for a site (the page starts on `demo-clinic`, the only demo site that has any), and press Run agent. The model named in the header and on the Configuration tab is labelled as declared, meaning the specification's default, while each run's own line says which model it actually ran on. The answer appears with its findings, with a report's headline and sections, or with an investigation's hypotheses under a banner saying they are not findings, and the fact ids it cites, together with the attempts, tokens and time, and View trace opens every step the run took, including each reply the model gave and why any attempt was rejected. Download JSON saves the full run record. The page is read only: it shows the agent's specification but does not edit it, and the buttons under the question are examples supplied by the agent's registry entry, including one question about cost and one about a forecast that the analyst should decline.

The page is three static files in `energyops/api/static` with no framework and nothing loaded from other sites. It is served with a strict Content-Security-Policy, only its own two assets can be fetched, and the script inserts everything that came from the server or a model as text, never as markup, so a hostile model reply cannot run code in the page. It is a stopgap for trying agents. The admin screens will be built properly in the web repository later and will replace it.

## The platform API and the web app

The platform API (`python -m energyops.service`) is the one the web app uses, and it is separate from the local playground API above. It needs a database and a signed-in person on every route except `GET /health` and, in the local environment only, `POST /auth/dev-login`. Its full description is generated from the code: `uv run python -m energyops.service.openapi web/openapi.json` writes it, the web app's types are generated from that file, and a test fails if the committed copy is out of date. Serve it locally and open `/docs` for the readable version.

The routes fall into groups: the signed-in person (`/me`), sites with their summaries, series, anomalies, tariff, forecast and uploads, the assistant (`/assistant/ask`), tickets and their decisions, knowledge documents and search, people and sites management for organisation administrators, usage and audit for the organisation, and the platform staff routes under `/admin` (agents and their settings, a playground for trying an agent, organisations, usage and audit across organisations). Platform staff can reach none of a customer's readings, documents or tickets.

Sign-in is checked on every request. Outside the local environment only Microsoft Entra access tokens are accepted. The local environment accepts short tokens that the backend itself issues for a seeded person. The token proves who someone is; their organisation, role and sites come from the database.

The web app calls these routes only from its server side. Its proxy route refuses paths for sign-in, health, the documentation and the API description, and refuses writes that do not come from the app's own origin.

## Uploading readings, forecasting and knowledge search

These routes belong to the platform API, not the local playground API, and every one needs a signed-in person whose role allows it.

`POST /sites/{slug}/readings/upload` takes a CSV file as the raw request body, with the header `timestamp,power_kw`. A timestamp is ISO 8601 and must carry its offset, because a file without offsets is refused rather than guessed at. Power is average kW over the interval that starts at the timestamp, never energy, and must be a plain non-negative number. Timestamps must sit on the meter's interval and appear once. The file is accepted whole or refused whole: a refusal answers 422 with the first twenty problems and their line numbers, and stores nothing. `dry_run=true` checks the file without storing it. Readings with the same meter and timestamp as stored ones replace them, and the answer says how many readings were already stored in the same time range so the person knows. Gaps are allowed and counted. The limits are 5 MB and 200,000 rows, and the size is enforced while the body is read. Only managers and organisation admins may upload, and only to sites they can see; any other site answers 404 exactly as an unknown one does. Each accepted upload is recorded in `ingestions` and in the audit log.

`GET /sites/{slug}/forecast?days=7` gives the next one to fourteen days after the last reading, at the meter's interval, with daily energy and peak demand. The method is the median of each weekday and time of day over complete past days, which is easy to explain and check but knows nothing about weather, holidays, closures or trend, and the answer says so. It refuses with a reason when there are fewer than 14 complete days, or fewer than two of any weekday. Every forecast carries a test: the same method is built from the days before the last seven days of history and used to predict them, and the error is reported next to the error of copying the same time a week earlier, with a plain `beats_naive` flag that is false when it does not win. With only the minimum history there is nothing left to test on, and the answer says that instead of showing a score.

`POST /knowledge/documents?title=...` takes plain text or markdown as the body (up to 1 MB and 400 passages), `GET /knowledge/documents` lists them, `DELETE /knowledge/documents/{id}` removes one, and `GET /knowledge/search?q=...` returns the closest passages of the caller's own organisation, written exactly as they were uploaded, with the document and a score. Nothing summarises or rephrases them. Uploading and deleting need the manage knowledge permission; searching only needs view data.

The embedder is chosen at start-up. With `ENERGYOPS_EMBEDDINGS_BASE_URL`, `ENERGYOPS_EMBEDDINGS_API_KEY` and `ENERGYOPS_EMBEDDINGS_MODEL` set, the service calls that OpenAI compatible `/embeddings` endpoint, which is exercised here only against a fake transport, never a real provider. The answer must be 768 numbers per passage, and a provider that returns another size produces a clear error rather than a truncated vector. `dimensions` is sent because OpenAI documents it for its newer models, and `ENERGYOPS_EMBEDDINGS_SEND_DIMENSIONS=false` leaves it out for a provider that rejects it. Without those settings, every environment except production falls back to a hashing embedder that matches shared words and word pairs only; results say plainly that they come from word matching and not meaning. Production without a provider turns knowledge search off (503).

The supervisor can reach both: a question about next week's demand goes to the forecast, and a question about a procedure goes to knowledge search, each for the person asking and on their own site and organisation only.
