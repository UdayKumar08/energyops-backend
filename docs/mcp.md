# MCP servers

MCP, the Model Context Protocol, is a standard way for a program to offer tools to an AI application. We use it so that agents reach our data through a small, explicit, inspectable interface and not through code they can wander around in. We build servers with the official Python SDK, `mcp` version 2, whose server class is called `MCPServer`.

The first server is `energyops.mcp_servers.energy`. It is read only by construction and says so to every client: both its tools are marked as read only, not destructive, idempotent and closed to the outside world. Its two tools are `list_sites`, which returns the demo site ids and the default site, and `get_fact_sheet`, which takes one site id and returns the numbered fact sheet for it, with each figure's exact display text, the notes about any missing data, and the same prompt text an agent would be given. Every number comes from our own Python functions, and a test compares the tool's answer to those functions figure by figure. The site argument is required on purpose. In an early version it was optional, and a call with a misspelled argument name quietly returned the default site's figures, which is the kind of wrong answer a model would never notice, so now it fails with a clear message instead. Nothing in the server takes a file path or a web address, and it reads only the built-in demo data.

The server talks over stdio, which means a client starts it as a subprocess and exchanges messages over its standard input and output. That is why nothing in the server may print to standard output. There is no network port and no sign-in to worry about, because the only thing that can talk to it is the program that started it.

To see it work, run `uv run python -m energyops.mcp_servers.check`. It launches the server as a subprocess exactly as an agent would, lists the tools, and prints the first fact for each site. It uses no model and needs no key. A fact sheet fetched over MCP can be turned back into the same `FactSheet` object that Python computes, using `FactSheetModel.to_fact_sheet`, so the figure check in the energy analyst works on it unchanged. 
## How the energy analyst uses it

The energy analyst now fetches its fact sheet through this server by default. Python decides which tools to call and in what order, and the model never chooses a tool, so the agent stays a fixed pipeline: with no site named it calls `list_sites` to learn the default and then `get_fact_sheet`, and with a site named it calls only `get_fact_sheet`. Each call is recorded in the run's trace as a `tool_call` step with the server, the tool, the arguments and whether it failed, and the fact sheet it produced is recorded in a `fact_sheet` step that says whether it came `via` mcp or direct. A direct path, which computes the same fact sheet in Python without any tool call, is kept so the two can be compared, and a test checks that the model is shown exactly the same prompt either way.

This is where the agent's permissions in its specification start to mean something. The spec lists the MCP servers it may use and the tools it may call, and the code refuses anything outside those lists before making a single call. It also refuses any tool that does not declare itself read only, even one the spec allows, so a server that later gains a tool that writes cannot be reached by this agent by accident. A server that cannot start, a tool the server does not offer, a reply in the wrong shape and a call that takes longer than the agent's timeout each end the run as a failed record with its own reason, `tool_error` or `tool_timeout`, never as a crash. Expected failures from the server carry a stable code before the message, `unknown_site` or `unusable_data`, so the agent reports them as the same kinds of failure a direct run reports.

Starting the server as a subprocess for each run costs about a second on a development machine, which shows in the `fact_sheet` step, while the tool calls themselves take tens of milliseconds. That is fine for a local playground and is the first thing to change when the server becomes a long-running service.
